# Admin Panel & Access — reference

How to reach the LibreChat Admin Panel, the accounts/roles that exist, and how to manage and
test access. Part of the access-control epic (see `docs/PRODUCTION-READINESS.md`, `AC-*`).

> **Passwords are NOT in this file (or any committed file).** Current local test-account
> passwords live in the git-ignored `chat/admin-credentials.local.md`. Never commit credentials.

## Admin Panel

- **URL (local):** http://localhost:3091 (the `admin-panel` service in `chat/docker-compose.yml`).
- **What it does:** manage custom **roles**, **groups**, permission **grants**, and
  config overrides. Talks to the LibreChat API only (not Mongo directly).
- **Requires** LibreChat **v0.8.5+** (we run v0.8.7).
- **Session secret:** `ADMIN_PANEL_SESSION_SECRET` in `chat/.env` (generated by `init-env.ps1`).
  This signs sessions — it is **not** a login password.
- **⚠ Security:** the panel is a powerful admin surface. `:3091` is for **local dev only**. In
  production it MUST sit behind the reverse proxy with auth + an IP allowlist (ties `P0-1`).

## Who is an admin

Admin access is one of:
1. The **first-registered** LibreChat user (auto-admin).
2. A user with `role: 'ADMIN'` set in MongoDB.
3. A principal granted the `access:admin` capability.

Log into the Admin Panel with an admin account (same credentials as the LibreChat UI :3080).

## Roles (created in AC-1)

| Role | Intended audience | Intended scope |
|---|---|---|
| `noc-l1` | L1 support | dashboard + ticket/charger **status** reads |
| `noc-engineer` | field / NOC engineer | + live charger-proxy (GET-locked) |
| `noc-legacy` | legacy CMS users | `cms` MCP tools |
| `ADMIN` / `USER` | built-in | — |

Roles are created/edited under the panel's **Access → Roles** tab; membership via a role's
**Members** tab. Roles currently live in MongoDB only (reproducible-from-source is `P3-4`).

## Manage accounts (run from `chat/`)

```powershell
# Create a user (LibreChat CLI inside the api container)
docker compose exec api npm run create-user <email> "<Full Name>" <username> <password>

# Promote a user to admin
docker compose exec -T mongodb mongosh LibreChat --quiet --eval `
  'db.users.updateOne({email:"user@example.com"},{$set:{role:"ADMIN",emailVerified:true}})'

# Reset / change a password: log in as that user in the LibreChat UI (:3080) →
# Settings → Account, or re-run create-user semantics per LibreChat docs.

# Assign a role: Admin Panel → Access → Roles → <role> → Members → add the user.
```

## Testing role-based access

**Current state (important):** the `noc-l1` role is **assigned but not yet enforced**. The
things that actually *limit* a user are still to be built:
- **AC-2** — per-role **agents + ACLs** (an `noc-l1` user sees only the L1 agent, whose tools
  exclude the charger-proxy).
- **AC-5 / AC-6** — MCP-side **tool filtering + data scoping** (the server rejects/limits by
  role, resolving the shared-service-account gap `D2`).

So today, `noc-tester` has the same functional access as any user — the role is a label until
AC-2+ land.

**What you can verify now:**
- The role assignment: Admin Panel → Access → Roles → `noc-l1` → Members shows `noc-tester`
  (or in Mongo: `db.users.findOne({email:"noc-tester@quench.local"})`).
- The test user can log into `:3080`.

**How to test limited access after AC-2 (the real test):**
1. Log into `:3080` as `noc-tester@quench.local` (has `noc-l1`).
2. Open the **agent picker** → confirm **only** the "NOC L1 Support" agent is visible
   (the "NOC Engineer" agent, shared to `noc-engineer`, must **not** appear).
3. Open the L1 agent's tools → confirm the **charger-proxy tool is absent**.
4. Negative check (after AC-5): even if a proxy call is attempted, the MCP server rejects it
   for the `noc-l1` role.

Compare side-by-side by logging in as an `noc-engineer` user (or the admin) and confirming they
*do* see the Engineer agent + proxy tool.
