Part 1 — Foundations

The five building blocks

Everything in Manthan is assembled from five kinds of thing. Understanding how they relate is most of the job.

ROLE— sees → AGENT— uses →MODEL (the brain: which LLM)
USER— assigned to a role
AGENT — carries → MCP TOOLS(actions: query a system)
AGENT — carries → KB TOOL(retrieval: search documents)
BlockWhat it isDefined in
MCP serverA set of tools that read/act on one backend system.docker-compose.yml + librechat.yaml
Knowledge baseSearchable documents, exposed as a kb_search_<profile> tool.knowledge/ + scopes.yaml
ModelThe LLM that reasons (GLM today; Claude/others pluggable).librechat.yaml → endpoints
AgentOne model + a chosen set of tools + an instruction prompt.agents.json → MongoDB
RoleA label on users deciding which agents they see + whether they may use tools.Admin Panel → MongoDB
The mental model

You build tools and knowledge, bundle a selection into an agent with a model, then use roles to decide which users see which agents. A department is just "a role + the agents shared to it + the tools and knowledge those agents carry."

Flow A — The request path

What happens when a user asks a question

Nothing the user types ever reaches a backend system directly. Every request travels this path.

1UserTypes a question in the web UI, inside a chosen agent.
2Role checkLibreChat checks the user's role — is this agent shared to them, and may they use agents? If not, the agent isn't shown / its tools are stripped.
3To the modelThe question + the agent's instructions + the agent's tool list are sent to the agent's model.
4Model decidesThe model picks which tool answers the question and returns "call tool X with args Y".
5Tool layerLibreChat routes the call to the right MCP server (by the tool's name suffix). The server holds the credential, runs the real query, returns real data.
6Model answersThe model reads the returned data and writes the answer, citing KB sources if the knowledge tool was used.
7User + auditThe user sees the answer. The whole exchange is stored in MongoDB, auditable later.
Four facts to internalise

The model never holds a password and never talks to a backend directly — it only asks LibreChat to run a tool. A tool the agent doesn't carry does not exist for that chat. Tool names encode their server — dashboard_summary_mcp_noc routes to the noc server. "No tools available" is usually a missing permission, not a bug (see Flow F).

Flow B — New capability

Adding an MCP server (a new set of tools)

An MCP server turns one backend system into safe tools. Adding one is four edits + a restart — no LibreChat code changes.

 build server dir        docker-compose service       librechat.yaml
 <name>-mcp-server/  ───▶  builds + runs it       ───▶  (a) mcpServers.<key> = its URL
 (FastMCP, its tools)      on an internal port           (b) allowedAddresses += host:port
                                                                 │
                                     restart the stack  ────────▶ LibreChat connects, lists its
                                                                  tools → available to attach to agents
  1. Build the server in <name>-mcp-server/ — copy chargezone-jira-mcp-server/ as a template.
  2. Add a compose service and register it in librechat.yaml in two places (forgetting the SSRF allow-list is the classic mistake):
# apps/ai-platform/librechat/librechat.yaml
mcpSettings:
  allowedAddresses:
    - "sales-crm-mcp-server:8107"    # (a) SSRF allow-list — REQUIRED, easy to forget
mcpServers:
  sales_crm:                          # (b) the server LibreChat connects to
    type: streamable-http
    url: "http://sales-crm-mcp-server:8107/mcp"
    timeout: 60000

Put secrets in apps/ai-platform/librechat/.env, then cd apps/ai-platform/librechat && ./up.ps1. Verify with docker logs noc-librechat | grep "[MCP][sales_crm]".

Not done yet

Adding a server makes its tools available. An agent must explicitly carry them (Flow C) before any user can trigger them.

Flow C — The assistant

Creating an agent

An agent is what a user talks to: one model + a curated set of tools + an instruction prompt. Choosing its tools is choosing what that assistant is allowed to do.

 Agent Builder (in the UI)  ──creates──▶  agent in MongoDB  ──served──▶  appears in the agent
  • pick model                                    │                       picker (to whoever
  • pick tools (any MCP server + KB)              │  export-agents ▼       it's shared with)
  • write instructions                            └──────────▶  apps/ai-platform/librechat/agents/agents.json
  • set sharing (which roles)                                   (version-controlled source of truth)
StepDo this
ModelChoose the LLM — glm-5.2, or a Claude model once added (Flow E).
ToolsAdd the tools this agent carries — from any MCP server + the right kb_search_<profile>. This is the capability boundary. A Sales agent gets CRM tools + kb_search_sales; not the NOC charger tools.
InstructionsWrite the system prompt — identity, behaviour, when to use the KB, when to clarify before acting.
SharingShare to the role(s) that should see it (Flow F). Unshared = only you see it.
Persistcd apps/ai-platform/librechat/agents && ./export-agents.ps1 → commit agents.json.
Gotcha

agents.json is regenerated by export. If you hand-edit the file, run restore-agents.ps1 immediately (then restart api), or the next export silently overwrites your edit.

Flow D — Knowledge

Giving an agent its own knowledge base

The KB is agent-centric: different agents can have completely different document pools. A Sales agent can search sales collateral while being unable to retrieve an HR policy — bound server-side, not by the prompt.

 knowledge/<scope>/*.pdf  ──ingest──▶  vectors in Qdrant
        │                                  ▲
 scopes.yaml: scope + profile             │ filtered by scope, SERVER-SIDE
        │                                  │
        └────────▶  one tool per profile:  kb_search_<profile>
                    (an agent with kb_search_sales can ONLY reach the sales scope;
                     the model cannot ask for a scope it wasn't given)
# knowledge/scopes.yaml
scopes:
  sales:
    folder: sales
    # confidential: true      # → its own Qdrant collection (physical separation)
profiles:
  sales:
    scopes: [sales]
    description: "Sales collateral, pricing, product sheets."

Then ingest and register the tool:

docker exec kb-mcp-server python -m kb_mcp.ingest --prune
docker compose restart kb-mcp-server        # so kb_search_sales registers

Attach kb_search_sales to the Sales agent (Flow C), and record the load in knowledge/MANIFEST.md.

Retrieval ≠ access control

Anything ingested into a scope can be quoted to anyone whose agent holds that scope's tool. Isolation comes from which agent gets which kb_search_ tool — never put material in a scope its agent's users shouldn't see.

Flow E — The brain

Adding or swapping the AI model

Each agent names one model. Models come from endpoints in librechat.yaml. Add a provider and its models become selectable on any agent.

# apps/ai-platform/librechat/librechat.yaml
endpoints:
  custom:
    - name: "GLM"                       # existing
      apiKey: "${GLM_API_KEY}"
      baseURL: "https://api.z.ai/api/coding/paas/v4"
      models: { default: ["glm-5.2", "glm-4.7"] }
    - name: "Anthropic"                 # new
      apiKey: "${ANTHROPIC_API_KEY}"
      baseURL: "https://api.anthropic.com/v1"
      models: { default: ["claude-opus-4-8", "claude-sonnet-5", "claude-haiku-4-5"] }

Add the key to apps/ai-platform/librechat/.env, run ./up.ps1, and the new models appear in the Model dropdown. Different agents may run different models — switch an agent's brain by changing its model and re-saving.

Data residency

For residency-sensitive deployments, Claude can be reached via AWS Bedrock in-region so inference stays inside your own cloud — see CLOUD-INFRA-ESTIMATION-BRIEF.md §3E.

Flow F — Access

Roles, users, and what each can see

This is the department mechanism. A role decides which agents a user sees and whether they may use tools at all. Managed in the Admin Panel at http://localhost:3091.

Step 1 · Create the role

Under Access → Roles → Create, add a role (e.g. sales). A label until you attach permissions and share agents.

Step 2 · Grant the two permissions a role must have (critical)

Creating a role and sharing an agent is not enough. Custom roles start with tool use off, so a shared agent will appear but reply "no tools available" — the model is sent zero tools.

PermissionWhy
AGENTS: USEMay use agents at all.
MCP_SERVERS: USEMay use the tools an agent carries — else tools are stripped before the model sees them.
 
docker compose exec -T mongodb mongosh LibreChat --quiet --eval `
  'db.roles.updateOne({name:"sales"},{$set:{"permissions.AGENTS.USE":true,"permissions.MCP_SERVERS.USE":true}})'
docker compose restart api            # restart so the permission cache refreshes

Step 3 · Create users and assign them

docker compose exec api npm run create-user <email> "<Full Name>" <username> <password>
# then: Admin Panel → Access → Roles → <role> → Members → add the user

Step 4 · Share the right agent to the role — and the result

In the agent's sharing settings, share it to only the role(s) that should see it. A role sees exactly the agents shared to it.

Verify any role

Log in as a user in that role → confirm the picker shows only their department's agent(s) → open the agent and confirm it carries only their tools + their kb_search_ profile. Compare against an admin, who sees everything.

Flow G — Lifecycle

What happens when you add or remove a role

ActionWhat changesWhat does not
Add a roleA label exists. No user affected until you grant permissions, assign users, and share agents.Anything, until those steps.
Assign a user to a roleOn next login they see the agents shared to that role.Their chats; their other roles.
Share/unshare an agentIt appears/disappears from that role's picker.The agent's config.
Change an agent's tools/KB/modelEvery user of that agent is re-scoped at once — this is how you re-scope a whole department.Who is in the role.
Remove a roleMembers fall back to remaining roles. Agents shared only to it become invisible.The agents, tools, KB — they persist, just unshared.
Remove a userThey can no longer log in.Everything else.
Reassigning KB / MCP / model to a department

= editing that department's agent. Swap its kb_search_ tool, add/remove MCP tools, or change its model. Because every user in the role talks to the same agent, one agent edit re-scopes the whole department. Role permission changes need an api restart; sharing and membership take effect on next login.

The cookbook

Onboard a new department (Sales / HR / Finance)

Every flow together. Example: stand up a Sales department, isolated from NOC.

#StepFlowResult
1Build/attach the MCP server(s) for Sales systems (CRM, pipeline).BSales tools exist
2Create knowledge/sales/, add a scope + profile, ingest.Dkb_search_sales exists
3Choose/add the model (existing GLM, or add Claude).EModel selectable
4Create the Sales Assistant agent = model + Sales tools + kb_search_sales + instructions.CThe assistant exists
5Create the sales role; grant AGENTS.USE + MCP_SERVERS.USE; restart api.FRole can use agents
6Share the Sales Assistant to the sales role only.FOnly sales sees it
7Create users, assign them to sales.FStaff onboarded
8Verify: log in as a sales user → only the Sales Assistant → only Sales tools + kb_search_sales.FIsolation confirmed
9Share all agents to the management role for the org-wide override.FManagement sees all

Repeat for HR, Finance, etc. Each department is its own agent(s) + role + scope + tools on the same shared platform. Nothing about the platform is NOC-specific.

Read before loading sensitive data

How isolation actually works

Be precise about this before loading HR, Finance, salary or PII.

Enforced today

  • Agent visibility by role — a user sees only agents shared to their role (proven in Flow F).
  • Capability by agent — an agent triggers only the tools it carries; the model never sees the rest.
  • Tool-use permission by role — without MCP_SERVERS.USE, all tools are stripped.
  • KB scope binding — kb_search_<profile> is locked to its scope server-side; confidential scopes get a separate collection.

Not yet enforced (Gate 2 / D2)

  • Per-user identity at the MCP layer. MCP servers use a shared service account to reach each backend.
  • So isolation rests on which agent a user can reach — not on the backend refusing a cross-department request if reached.
  • The deeper control (each user's identity carried to the tool, per-department credentials, the server rejecting out-of-scope requests) is the enforcement gate in PRODUCTION-READINESS.md (AC-5/AC-6, D2).
Practical rule until Gate 2 lands

Treat agent + role scoping as good access control for trusted internal users, not a hard wall against a determined insider. For genuinely sensitive data, either wait for MCP-side enforcement, or give that department a dedicated MCP server with its own scoped credentials so it physically cannot read another department's data.
