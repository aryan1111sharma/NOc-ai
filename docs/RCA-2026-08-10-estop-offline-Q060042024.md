# RCA — E-stop while offline, Q060042024 (VinFast UAT), 2026-08-10 11:21–11:26

## Context

**Reported defect.** Reproducible field scenario with non-deterministic outcome:

```
1. Start charging
2. Take the charger OFFLINE (kill CSMS connectivity)
3. Press the emergency stop
→ Outcome varies:
   (a) sometimes the database locks
   (b) sometimes the session stops cleanly but the EV cannot be unplugged
```

**The supplied log is an instance of this scenario.** The charger was offline from before 11:21:00
(DNS failures, reconnect attempts 19–21) when the E-stop was pressed at 11:21:52. It exhibits
symptom (b): `StopTransaction` succeeded with `reason=EmergencyStop`, yet the connector stayed
engaged for a further **2 min 23 s**.

This document maps the two reported symptoms onto log evidence, then lists the remaining defects
found in the same window.

**Constraint on this analysis.** The charger controller source is not in this repository (`grep`
for `charging_polling`, `ocpp_client_v16_enhanced`, `CP_STATE_F_SET`,
`allocation_manager_powercube` returns nothing). Findings are marked **Evidence** (shown in the
log) or **Inference** (deduced — needs source or bench confirmation).

## Assumptions

1. OCPP **1.6J**, charge point role; CSMS `cpo-wss-internal-uat.cloudcpo.net:9462` (UAT).
2. `cp` maps `0=A, 1=B, 2=C, 3=F` per the log's own legend.
3. `Energy.Active.Import.Register` @ `Outlet` is cumulative Wh, monotonic, and is the register
   behind `meterStart`/`meterStop`.
4. Vendor `3-105-0` = physical E-stop; `1-257-2` / `1-156-2` / `2-217-2` = SLAC / EV-comm /
   EV-disconnect.
5. `/app/qflex/db/charging_controller/evse.db` is **SQLite** and is shared by the OCPP offline
   message queue, `charging_sessions`, and `FirmwareDiagnostics`. *(Gates the symptom (a) hypothesis.)*
6. `switched_on_controller_pins_do` / `ac_switched_on_controller_pins_do` drive **contactors**,
   not indicator-only signals. *(Gates finding C-2 — least certain assumption.)*

# Part 1 — The two reported symptoms

## Symptom (b): "session stops but EV cannot be unplugged" — ROOT CAUSE FOUND

**Evidence.** From 11:22:41 to 11:24:30, on a ~5.1 s cycle, **21 times**:

```
[CP_F] Gun 2: CP_STATE_F_SET timeout (cp=1), skipping RESET_SECC
SECC control Gun 2: CP_STATE_F_SET
SECC control Gun 2 CP_STATE_F_SET command accepted by M7
[CP_F] Gun 2: error_stop_triggered=True (session aborted by State F)
```

M7 **accepts** `CP_STATE_F_SET` every single time, yet `cp` never leaves `1` (State B). The loop's
exit condition — observing `cp == 3` — is never satisfied while the cable is inserted.

**The mechanism is a deadlock, and it is visible in one line:** `skipping RESET_SECC`.

`RESET_SECC` is the action that actually releases the connector. It is gated behind the CP-State-F
confirmation that never arrives. So:

> **The release action is blocked by a precondition that cannot become true while the
> connector is engaged.**

**What finally broke the deadlock** — two escape hatches, neither of which is the intended path:

| Time | Trigger | Result |
|---|---|---|
| 11:24:15 | `[CP_TRANSITION] Gun 2: CP 1->0 detected` — cable physically removed | `[SESSION_ABORT] … sending STOP + RESET_SECC` |
| 11:25:45 | System error cleared (E-stop released) | `[CP_F] RESET_SECC sent (system error cleared, SECC SoftReset)` |

Both require the operator to act first. **While the E-stop is held and the cable is in, there is no
path to release.** That is precisely the reported symptom.

**Why "sometimes".** Two candidate sources of non-determinism, both **Inference**:

1. **The 15 s SECC blind window.** `[SECC-RESET] Gun 2: Ignoring SECC frame data for 15s while M7
   SECC settles`. If the CP transition that would satisfy the loop lands inside this window, it is
   discarded and the loop continues. Whether it lands inside depends on timing → non-deterministic.
2. **Whether CP happens to be at 0 or 1 when the E-stop is asserted.** At 11:24:30 the same loop
   ran with `cp=0` and `elapsed=16.2s` — the timer behaves differently across CP states.

**Fix (minimum safe change).** Bound the retry and stop starving the recovery path:

- Add an attempt ceiling (3 attempts ≈ 15 s) to the `CP_STATE_F_SET` loop.
- On ceiling, **issue `RESET_SECC` regardless of CP state** and raise a distinct vendor error so
  the field sees why.
- Do not swallow CP transitions during the 15 s SECC settle window — buffer and replay them.

This closes the deadlock without touching the underlying M7 question, which is separate and slower
to resolve (below).

**Open question requiring bench work.** Why does a command M7 acknowledges produce no CP
transition? Three candidates, distinguishable only with a scope on the CP line: M7 does not drive
the pilot; the EV holds State B against it; or the readback reports EV-side CP rather than
commanded state. **This is a firmware/hardware investigation, not a controller fix.**

**Test case.** EV connected, charging, CSMS offline. Assert E-stop. Assert: `RESET_SECC` is issued
within 20 s **without** operator intervention, and the connector releases.

## Symptom (a): "the database locks" — HYPOTHESIS, not confirmed

**This log does not contain a `database is locked` error.** I will not claim it is explained. What
the log does establish is the contention that would produce it:

**Evidence of shared-writer contention on one SQLite file:**

```
[FirmwareDiagnostics] Manager initialized (db_path=/app/qflex/db/charging_controller/evse.db)
Gun 2: ConnectorUnplugged check — … db_path='/app/qflex/db/charging_controller/evse.db'
StopTransaction transactionData (from charging_sessions): SoC start=17%, stop=17%
```

Three subsystems on one file. Now add the offline burst: messages **1724 → 1748** (25 queued
messages) were persisted while offline and drained in ~13 s on reconnect, each drain performing a
read, a send, and a dequeue write — concurrent with `charging_polling` writing session state every
poll and the error manager writing fault records.

```
Observation:  DB locks intermittently when the E-stop is pressed while offline.
Hypothesis:   The offline queue accumulates writes; the E-stop simultaneously triggers session-abort
              writes, error-manager writes, and (on reconnect) a rapid drain — exceeding SQLite's
              busy_timeout with no WAL mode, producing SQLITE_BUSY.
Test:         grep the full log for "database is locked" / "SQLITE_BUSY" / "OperationalError";
              and run `PRAGMA journal_mode;` + `PRAGMA busy_timeout;` on evse.db.
```

**Two `PRAGMA` values decide this.** If `journal_mode=DELETE` (the default) and `busy_timeout=0`,
the hypothesis is almost certainly correct and the fix is one line: `WAL` + a busy timeout of a few
seconds. If it is already `WAL` with a timeout, the cause is elsewhere — most likely a long-running
write transaction held open across the E-stop handler.

**I need the full log (or the two PRAGMA values) before proposing a fix here.** Everything above
for symptom (b) stands on its own evidence; this does not yet.

# Part 2 — Other defects in the same window

Root cause of the *event* was a genuine physical E-stop (`3-105-0`, "EMERGENCY PRESSED", system
register `0x00000001`), cleared at 11:25:38 — a **3 min 46 s** outage. The charger's top-level
response was correct: fault all connectors, abort the session, `reason=EmergencyStop`, suppress
AutoCharge while faulted, recover on clear. The following were not.

## CRITICAL

### C-1 — The transaction billed 0 Wh while ≥134 Wh was delivered

`meterStart = 14764` (11:21:49) and `meterStop = 14764` (11:22:26) are identical.

```
1. Formula:    E_billed = meterStop − meterStart
2. Units:      Wh − Wh = Wh ✓
3. Substitute: E_billed = 14764 − 14764
4. Compute:    0 Wh
5. Recheck:    14764 − 14764 = 0 ✓
6. Assumption: same cumulative Outlet register (Assumption 3)
7. Edge:       0 Wh with non-zero power must be flagged, never billed silently
```

Energy *was* flowing before `meterStart` latched:

```
1. Formula:    ΔE = E(11:21:51) − E(11:21:12)
2. Units:      Wh − Wh = Wh ✓
3. Substitute: ΔE = 14764 − 14630
4. Compute:    134 Wh
5. Recheck:    14764 − 14630 = 134 ✓
6. Assumption: monotonic, no rollover in 39 s
7. Edge:       negative Δ ⇒ rollover ⇒ discard, do not bill
```

Independent cross-check from reported power:

```
1. Formula:    E = P × t
2. Units:      W × s ÷ 3600 = Wh ✓
3. Substitute: E = 13439 × 39 ÷ 3600
4. Compute:    145.6 Wh
5. Recheck:    13439 × 39 = 524,121 W·s ÷ 3600 = 145.6 Wh ✓
6. Assumption: constant power — it was NOT (ramped to 0 by 11:21:51)
7. Edge:       ramp-down ⇒ actual < 145.6 Wh, consistent with 134 Wh measured
```

Two methods agree, and the charger's own `Energy.Active.Import.Interval = 134` at
`Transaction.Begin` confirms it knew. **Not E-stop-specific** — any session where power flows
before `StartTransaction` latches `meterStart` loses that energy on every occurrence, and the CSMS
receives a well-formed transaction with no indication anything is missing.

**Fix.** Latch `meterStart` at physical session start, not when `StartTransaction` is composed.
Add a CMS-side alarm for `meterStop == meterStart` where MeterValues show non-zero
`Power.Active.Import` — this catches it fleet-wide **without a firmware release**.

### C-2 — Contactors appear to close during an active E-stop *(Inference — gated on Assumption 6)*

At 11:22:53.87, with `3-105-0` active on all connectors:
```
'switched_on_controller_pins_do':    [] -> [7]
'ac_switched_on_controller_pins_do': [] -> [8]
guns_updated_pms:                    {} -> {'2': [2, 1]}
```
All reversed 1.2 s later at 11:22:55.06. `sink_module_assigned` then cycles False→True→False.

If pins 7/8/23/24/25 are contactor drives, the allocation engine commanded closure during an
emergency stop. **Confirm against the pin map before escalating** — this is the finding I am least
able to settle from logs.

**Fix.** Gate the allocation engine on `has_system_error`: no PM assignment, no pin switching while
a SYSTEM error is active on that gun.
