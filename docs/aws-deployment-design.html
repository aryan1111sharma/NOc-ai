The decision

One EC2 instance, not a Kubernetes cluster

This reverses DEP-1 in PRODUCTION-READINESS.md, which specifies “Kubernetes, not ECS/App Runner”. The reversal applies to stage 1 only, and it needs a sign-off from whoever owns that decision.

Recommended Single t3.large running the existing docker-compose.yml, unchanged
01 Portability points the other way DEP-1 chose Kubernetes to satisfy D3 (no cloud lock-in). But a compose file runs on any VPS, any cloud, a laptop, or k3s. Helm is the heavier portability story, not the lighter one — so D3 is satisfied more cheaply by staying where we are.
02 There is no scaling problem yet The estimation brief itself states concurrency is low — roughly five concurrent chats at Tier A — and that latency sits in the LLM API, not our compute. It also sets RPO 24 h / RTO 1 business day against a 99.5% business-hours target. A single instance with nightly snapshots already meets that. Multi-AZ HA would buy availability the requirements do not ask for.
03 The compose file carries load-bearing detail The pinned project name chat — whose own comment warns that changing it silently orphans every user account and chat history — plus the bind-mounted departments.json and the SERVER_HOST default that prevents a startup crash loop. Translating fourteen services into Helm charts is exactly where details like those get dropped.

Revisit EKS when any one of these becomes true: a platform team takes ownership, user count passes ~150, or DEP-15 (registering new MCP servers without a stack redeploy) becomes a firm requirement. The VPC, ECR, secrets and state layout below are all reusable, so that later move is a migration rather than a rewrite.

Options considered

Three ways to host fourteen containers

Chosen A · EC2 + compose ~$152 / mo One instance, the stack we already run, Terraform-managed. We know how to operate it today. Costs: single AZ, roughly two minutes of downtime on redeploy, vertical scaling only.
Rejected B · ECS Fargate ~$200–260 / mo The three stateful services are the blocker. Fargate's storage story is EFS, and MongoDB on EFS is a known-bad pairing — making it work means pushing Mongo to Atlas or DocumentDB. More cost, more lock-in, and the least portable of the three.
Deferred C · EKS, per the brief ~$300–450 / mo Genuinely the right destination at Tier B, and the only option that serves DEP-15 elegantly. But it hands a solo operator with no Kubernetes background a cluster needing version upgrades roughly every four months, plus IRSA, CSI drivers and fourteen services of Helm charts.

Architecture

What gets built

The instance has no public IP and accepts traffic only from the load balancer's security group. Keeping the data volume separate from the root volume makes the instance disposable — it can be replaced, resized or re-imaged without touching MongoDB, Qdrant or Meilisearch data.

Storage

What grows, and where it lives

Five of the nine state stores have no ceiling, and a sixth is unverified. The one people underestimate is MongoDB, and it is specific to this stack: LibreChat stores full message content, and our messages carry tool results — charger telemetry payloads, ticket dumps, fleet queries. Meilisearch then indexes all of it again. So the two largest consumers both scale with tool-call volume, not with user count.

Correction · the knowledge corpus exists in exactly one place

knowledge/ is a bind mount, not a Docker volume, so setting Docker's data-root to the EBS volume does not capture it — it lands wherever the deploy tree sits. Left on the root volume that gives two failures: KB uploads fill an 8 GB root disk and take the box down, and the corpus is absent from the daily snapshot, so replacing the instance loses it. That second one bites hardest because knowledge/.gitignore deliberately excludes the corpus as “large or proprietary” — those documents are in no git history and no other backup. Today: 25 MB across 74 files, 24 MB of it dept-noc/.

The fix is that nothing stateful sits on the root volume. Both bind mounts move onto the snapshotted EBS volume, and the corpus joins the nightly S3 sync alongside the database dumps — it needs the offsite copy more than they do, since they at least rebuild from their own dumps. 

/data/                          ← EBS gp3, encrypted, snapshotted daily
├── docker/                     ← data-root: all 8 named volumes
└── app/                        ← deploy tree (compose + bind mounts)
    ├── knowledge/              ← KB corpus · nightly S3 sync
    └── roles/departments.json  ← created by deploy script before compose starts

That last line matters more than it looks: if departments.json is missing, Docker creates a directory at that path instead of failing, and every kb_admin_* call breaks with no obvious cause. On a fresh instance the file must exist before the stack starts.

Sizing. 100 GB gp3 is comfortable for a 25-user pilot — realistically single-digit GB in year one. Two things make that safe rather than lucky: gp3 resizes online, so 100 GB is a starting point rather than a commitment, and the disk alarm at 80% turns “we ran out of disk” into “we grew the volume last month”. The wildcard is the corpus — if a department loads a few GB of manuals, Qdrant's vectors grow alongside it.

Read this first

What deploying to AWS does not fix

P0-7 · blocks any multi-user launch

The configured z.ai GLM endpoint is a Coding Plan, whose terms prohibit multi-user access and cap concurrency at roughly one in-flight request. Moving the stack to AWS does not change that — it makes a single-user-licensed endpoint the bottleneck for every user we onboard. This is a procurement action, not an infrastructure one, and it should run in parallel with the build rather than after it.

P0-2 · promoted to launch blocker

Because we chose public internet access, today's ALLOW_REGISTRATION=true would let anyone on the internet create an account and query live charger telemetry, tickets and customer data. Behind a VPN allowlist this was a follow-up item; on the open internet it is a launch blocker, and it is designed in rather than deferred.

How it's built

Design decisions worth arguing with

Each row names the production-readiness item it closes. Pills mark whether the design settles the item or leaves it open.

Network Private instance behind a NAT gateway Four subnets across two AZs — the load balancer requires two regardless, so the spare pair costs nothing and removes re-plumbing later. The instance sits private with no public IP, satisfying the brief's rule that all non-web services stay private. Access is SSM Session Manager only: no port 22, no key pairs, every session logged. Closes P0-3
DNS & TLS Delegate the zone to Route 53 One nameserver change at the registrar, then Terraform owns the zone for about $0.50/mo. This matters more than it sounds: with the zone in Route 53, ACM validates and renews the certificate indefinitely with no human action. Leaving DNS at the registrar means hand-adding a validation record — the classic step nobody remembers when re-validation is eventually needed. Closes P0-1
Identity Registration closed, ~25 admin-provisioned accounts Three layers: ALLOW_REGISTRATION=false, admin-created accounts, and a WAF rate limit on the login endpoint. Accepted trade-offs — passwords live in MongoDB, offboarding is manual, and there is no MFA, which makes that rate limit the only brute-force control we have. Revisit SSO before a second department joins. Closes P0-2
Secrets SSM Parameter Store — and Terraform never holds the values Roughly twenty SecureString parameters under /manthan/prod/*, encrypted with a dedicated KMS key. Not Secrets Manager: that costs about $8/mo for rotation we do not need. Each parameter is created with a placeholder and ignore_changes, then populated out-of-band — because if Terraform owned the values they would sit in plaintext in the state file, which is just .env with extra steps. At boot they render to a tmpfs path, so secrets never touch disk or enter an image layer. Closes P0-5, P0-6
Images Eight ECR repositories, built in CI via OIDC Eight distinct images, not fourteen: services/mcp/kb is built once and run twice with different commands, and the admin panel is an upstream image, not ours. Five third-party images get pinned to digests — mongo:7 and meilisearch:v1.12 are already tagged, so the real work is the three floating :latest tags. No long-lived AWS keys in GitHub. Closes P1-5
Deploy SSM Run Command, triggered from CI docker compose pull && up -d executed on the instance via an SSM document. No inbound connection, no SSH, no runner inside the VPC. Rollback is re-running it against the previous tag. A docker-compose.aws.yml override swaps builds for image references — the base compose file is not modified, so the local workflow survives intact. New
Backup Two layers, because they fail differently Daily DLM snapshots of the whole volume for fast recovery, plus a nightly mongodump, Qdrant snapshot and knowledge/ sync to S3. The second layer earns its place: a snapshot of a running mongod is only crash-consistent, and a logical dump also allows restoring one collection instead of the entire machine. Meilisearch is deliberately excluded — a rebuildable index, not a source of truth. The corpus is included precisely because it isn't rebuildable: it is in no git history. Meets RPO/RTO
Sizing t3.large is a deliberate bet, and it is tight Estimated resident footprint: Mongo ~1.5 GB, Qdrant ~1.5 GB, Meilisearch ~1 GB, LibreChat ~1.5 GB, the KB server's ONNX embedding model ~1.5 GB, headless Playwright ~0.75 GB, plus six Python MCP servers at ~200 MB — roughly 9–10 GB against 8 GB available. The failure mode is ugly: the OOM killer takes the largest process, usually Mongo, and it presents as unexplained random breakage. Mitigated by 4 GB swap, container memory limits, a memory alarm at 85%, and an instance type that is one variable away from doubling. Known risk

For comparison, the EKS design in the internal ballpark runs $300–450/mo. A one-year Savings Plan on the instance would bring this to roughly $135. Two levers exist if the number needs to come down further: dropping NAT for a locked-down public subnet saves $35 but formally breaks the brief's “no public IPs” rule, and dropping WAF saves $12 at the cost of our only brute-force control.

Before anything is applied

Five gates

None of these block writing the Terraform. All of them block go-live. Three are decisions rather than tasks, which is why this document exists.

1 Working AWS credentials Blocked aws sts get-caller-identity currently fails on the operator's machine, so terraform plan cannot run. Acceptance for this phase is therefore validate and lint clean, with a real plan deferred.
2 Move off the GLM Coding Plan (P0-7) Procurement A pay-as-you-go or approved provider tier whose terms permit multi-user access and whose concurrency clears projected peak. Start now; it has the longest lead time of anything here.
3 D1 — data residency ruling Decision Prompts and tool results — charger telemetry, tickets, customer data — are sent to Zhipu (z.ai, China-based) for inference. Internal use may accept this; a public-facing deployment warrants an explicit ruling on the record.
4 Nameserver delegation Task Point manthanquench.online at the Route 53 hosted zone. One change at the registrar; needed before ACM can issue.
5 The user list Task Roughly 25 accounts to pre-provision, since self-registration is closed.

Scope

Deliberately not in this phase

  • D2 — shared service-account identity. Every chat user still reads the entire fleet through one NOC_EMAIL token. Restricting tools does not restrict data. Unchanged by this deployment; tracked as AC-6.
  • DEP-15 — runtime MCP registration without a stack redeploy. Not achievable on single-instance compose; revisit with EKS.
  • A staging environment. The laptop remains staging for stage 1.
  • Multi-AZ or multi-region HA. Out of scope by design — see reason 02.
  • The deliverable is validated Terraform only. Nothing is applied and no AWS resource is created in this phase.
