How our knowledge base actually works

A plain-language walkthrough of the retrieval pipeline we built — and an honest read on whether Google's Open Knowledge Format has anything to do with it.

Part 1 — The build

Six stages, once per document

This runs when you add documents, not when you ask a question. It's a one-way chain: a PDF goes in the left, and searchable numbers come out the right.

01 Collect manuals, OCPP spec, runbooks → /knowledge
02 Read the pages PyMuPDF pulls raw text out of the PDF
03 Cut into slices every 1800 chars, 200 char overlap
04 Turn into numbers bge-base-en-v1.5 → 768 numbers per slice, runs locally
05 File them away Qdrant, collection ev_kb, cosine distance
06 Expose one tool FastMCP · kb_search() · port 8106

The one idea that makes it work: stage 04 converts a piece of text into a long list of numbers that captures roughly what it's about. Two slices about the same topic end up with similar numbers, even if they share no words. That's the whole trick — and it's also the source of the weakness further down.

Worth noting: those numbers are computed on our own machine. Documents never leave the box to get embedded, which is why the knowledge base sidesteps the z.ai data-residency question entirely.

Part 2 — The ask

What happens when someone asks something

The agent never searches text. It compares numbers to numbers.

Question "Why would a charger report a ground fault mid-session?"
Converted the same model turns the question into 768 numbers
Compared Qdrant finds the slices whose numbers sit closest
Filtered keep the top 5, drop anything scoring under 0.5
Returned 5 slices, each with its source, location and score
Answered the agent reads those 5 and writes the reply, citing each one

The 0.5 cutoff isn't a guess — on the sample corpus, on-topic slices scored 0.58–0.83 and off-topic ones 0.41–0.42, so the line sits in the gap. It will need re-checking once real manuals go in.

If nothing clears the bar, the tool returns an empty list and the agent is instructed to say the knowledge base doesn't cover it. That instruction is the only thing standing between us and a confidently invented answer.

Part 3 — The known gap

Where matching-by-meaning falls down

The failure case

Ask "what does error code 1079 mean?" and the system converts your question into numbers that mean roughly "a question about charger errors." The specific token 1079 barely survives that conversion — it carries almost no meaning, only identity.

So it returns five slices about errors in general, and the one slice that literally contains 1079 may not be among them.

This is the predictable weak point for our corpus specifically, because our corpus is full of exact tokens: error codes, OCPP configuration keys, part numbers, firmware versions, OCPP IDs. Those are lexical needles, not semantic ones.

Two standard fixes exist and we've built neither yet — a keyword search arm running alongside the number-matching, and a second-pass re-ranker. Both are deliberate deferrals, not oversights. I'd reach for the keyword arm first.

OKF is a way of writing the source documents: a folder of markdown files, one topic per file, each with a short label block at the top. It performs no search, stores nothing, and answers nothing.

So "OKF versus our RAG" isn't a real choice. The real question is narrower: should the documents we write ourselves be authored in that shape before they enter our pipeline?

Part 5 — Would it help

One place it genuinely would

Stage 03 — the slicing — is where neater source documents pay off.

Today: cut by character count

Error Code Table
1077 — Over-temperature
1078 — Contactor weld
1079 — Ground fault
✂ 1800 chars — cut lands here
   Action: isolate, then…

The slicer counts characters. It has no idea it just separated an error code from the instructions for fixing it.

With one topic per file

type: error-code
code: 1079
─────────────
1079 — Ground fault
Action: isolate, then…
✓ file ends — natural boundary

The boundary is meaningful, so the code and its fix stay together. The labels become things we can filter on.

The catch

Nobody is going to retype the OCPP specification and the vendor manuals into this format — and those are the bulk of the library. OKF realistically only covers the documents you write: runbooks, RCA writeups, the tribal knowledge currently in your head.

Part 6 — Recommendation

Steal the idea, skip the spec

Add labels to the slices we already make. Fields like doc_type, charger_model, ocpp_version, and let kb_search filter on them. Narrow the pile first, then match. This captures most of OKF's retrieval benefit, works on PDFs too, and commits us to nothing.

Write new runbooks as markdown with a label block on top. Whether or not that's formally OKF, it costs nothing over Word or Confluence and keeps the door open.

Don't restructure the corpus around an early-stage spec. I read the specification but haven't verified how widely OKF is adopted — and a plain folder of labelled markdown carries none of that risk.

One honest caveat on all of the above: the knowledge base currently holds only the Phase-1 sample documents. We're comparing filing systems before anything real is on the shelves. Loading actual manuals and watching where retrieval fails would settle these questions faster than any further analysis.
