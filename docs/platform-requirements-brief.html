Section 1 — What exists today

A working assistant for the NOC

Staff ask questions in a web chat. The assistant reasons, then calls the operations systems directly to fetch real answers — live charger state, open tickets, firmware versions — instead of guessing. Every connection is read-only by construction.

Live fleet Current NOC backend — chargers, sessions, alarms, telemetry. read-only
Legacy fleet (CMS) Older charge-management system still holding active estate. read + gated writes
Ecog Jira Vendor engineering tracker. read-only
Ecog Service Desk Vendor customer-facing tickets. read-only
ChargeZone Jira Customer tracker, hard-scoped to Quench's own project. read-only
Knowledge base Manuals, OCPP spec and runbooks, searched with citations. read-only
Document generation Turns results into downloadable spreadsheets and reports. output only

The safety model is structural, not procedural. The connections are built so that write operations are impossible rather than merely discouraged. The one deliberate exception — commands that reach a live charger — requires two-step confirmation and is fully audited.

Section 2 — How it works

High-level architecture

Five layers. A person never touches a business system directly — every request passes through a controlled tool layer that decides what is permitted, records what happened, and returns only real data.

Layer 1 People
NOC staff Service Sales HR Management Every user carries a role. The role decides which department they belong to.
Layer 2 Access
Web chat Company sign-in Role gate One interface for everyone. What you see inside it depends entirely on your role.
Layer 3 Assistants
NOC agents Service agents Sales agents Language models — swappable An agent is a job description: which model it uses, which tools it may call, how it should behave. Each is scoped to one department.
Layer 4 Tool layer
Read-only by construction Two-step confirm for writes Per-department credentials Audit trail The control point of the whole platform. Nothing reaches a business system except through here — which is why security is enforced at this layer rather than in the interface.
Layer 5 Systems & knowledge
Live fleet Legacy fleet Ticketing ×3 Knowledge base Reports ERP CRM HR systems The company's real systems of record. The platform reads from them; it does not become another place data lives.
Applies to every layer Identity & roles Who you are travels with the request, top to bottom. Audit trail Which tool ran, for whom, with what result. Secrets System credentials held centrally, never by the model. Data residency Where prompts and results are permitted to travel.

The important consequence: because Layer 4 sits between the assistant and every business system, adding a department means adding tools and a knowledge base — not rebuilding the platform. The same control point serves all of them.

Section 3 — One request, end to end

What actually happens when someone asks a question

A real example: an engineer asks how many high-priority tickets are open.

1 People An NOC engineer signs in and types the question in plain English.
2 Access Their role is checked. They are shown the NOC assistants — and no others.
3 Assistant The agent's model reads the question and decides which tools can answer it.
4 Tool layer The request is checked against what that department is permitted to do, run with that department's own credentials, and recorded in the audit trail.
5 Systems The ticketing system is queried live. Real numbers come back — nothing is recalled from memory or estimated.
6 Assistant The agent turns the result into an answer, citing where each figure came from.
7 People The engineer gets the answer in seconds, with the source shown so it can be checked.

Step 4 is where the platform earns its trust. The model never holds a password and never talks to a business system directly. It can only ask the tool layer, which decides whether the request is allowed — and writes down that it happened.

This is also why a request that has no answer in our systems returns nothing rather than a plausible guess. The assistant reports what the systems said, or reports that it does not know.

Section 5 — What the platform must do

Functional requirements

R1 One platform, many departments The same chat platform serves Service, Sales, HR and others — not a separate tool per team. Proven
R2 Per-department tooling Each department gets its own tools and knowledge base, talking to that department's systems. Proven
R3 Per-department agents Agents are scoped to a department and carry only that department's tools and knowledge. Proven
R4 Role-based user assignment Users are bound to roles; a role sees only its own department's agents. Visibility only
R5 Management override Top management holds a role granting access across all departments' agents. Proven
R6 Updatable knowledge bases Each knowledge base can be refreshed over time — ideally self-service, not developer-only. Developer-run
R7 Pluggable models Models can be added or swapped centrally; different agents may run different models. Proven

R4 carries the one caveat that matters. Today the role controls what a user sees. It does not yet stop a determined user from reaching another department's data underneath. Closing that gap is Gate 2 below, and it is the single most important item on this page.

Section 6 — What it must satisfy

Non-functional requirements

N1 Multi-user licensing Model access licensed for company-wide concurrent use. The current plan does not permit it. Gate 1
N2 Real data isolation Department separation enforced in the tool layer — per-user identity and per-department credentials — not just hidden in the interface. Gate 2
N3 Security baseline TLS, company SSO with closed registration, database authentication, managed secrets, internal-only service ports, protected file downloads. Gate 3
N4 Data residency compliance Prompts and results — including HR data — must not leave approved jurisdictions. Needs provider sign-off or self-hosted models. Decision open
N5 Auditability Tool calls logged, especially writes. Today only charger commands and legacy-system writes are audited; this must generalise. Partial
N6 Repeatable onboarding Adding a department follows a documented recipe rather than bespoke engineering each time. To document
N7 Scalability path Single host for the pilot; cloud infrastructure once department count or availability demands it. Direction already agreed. Decided

Section 7 — The decision

Three gates stand between pilot and rollout

The platform works. These are not engineering unknowns — each one needs a commercial or organisational decision before it can be closed.

Gate 1

Licensing

The model plan powering the assistant today is licensed for individual development use, not company-wide concurrent access. Rolling out to multiple departments on the current plan would breach its terms.

Needs: an enterprise model agreement, budgeted per seat or per usage.

Gate 2

Enforcement

Department separation is currently enforced by what each role can see. Before HR or Sales data enters the platform, separation must be enforced where the data actually lives — carrying each user's identity through to the tool layer, with credentials scoped per department.

Needs: engineering time, plus a decision on the shared-identity model.

Gate 3

Hardening

The pilot runs on a single internal host with development-grade settings. Company-wide use requires encrypted traffic, sign-in through company accounts with open registration closed, authenticated databases and managed secrets.

Needs: engineering time and IT coordination for SSO and certificates.

Running alongside these is data residency: confirming that prompts and results stay within approved jurisdictions. That is a provider question first and an engineering one second — and it becomes non-negotiable the moment HR data is in scope.

Section 8 — Boundaries

Decisions already taken, and what is deliberately excluded

Settled principles

  • Read-only first. Writes are two-step, confirmed, audited and never retried automatically.
  • Customer data stays separate. Each ticketing tenant keeps its own connection; they are never blended.
  • Capabilities arrive as tools. The platform extends one way, which keeps the security review surface small.
  • Knowledge stays on our machines. Document indexing runs locally — knowledge-base content is never sent out for processing.
  • Cloud when justified. Single host for the pilot, cloud infrastructure once scale demands it.

Out of scope for now

  • Filtering individual tools in the interface. Not possible at this layer; it has to be enforced in the tool layer instead — which is Gate 2.
  • Autonomous alarm handling. Would conflict with the read-only posture; held pending a separate decision.
  • Self-service knowledge upload. Content is loaded by a developer today. Worth building, not yet built.
  • ERP integration. Blocked on programmatic access. Driving the ERP's screens automatically was considered and rejected as too fragile.

Section 9 — What we need

Where this needs a management decision

Three asks, in order

1. Approve an enterprise model licence. Nothing rolls out beyond the NOC pilot without it, and it sets the per-seat cost basis for every department that follows.

2. Confirm which department goes second. The pattern is proven once; proving it a second time is what turns it from a working system into a repeatable one. Service is the natural candidate.

3. Rule on data residency before HR is in scope. This determines whether we can use a hosted model at all, or must run models on our own infrastructure — a materially different cost and timeline.

Engineering work for enforcement and hardening can begin in parallel and does not block on these decisions — but rollout does.

Status summary. The platform is built, running and in daily use by the NOC team against live operational systems. What remains before company-wide rollout is not proving the concept — it is licensing it correctly, enforcing separation properly, and hardening it for production.
